# /bugfix — 버그 수정 (T4 BUGFIX, 개발2팀 주관)

버그 보고: $ARGUMENTS

너는 Ultra 프로젝트의 버그 수정 절차를 수행한다. 버그 수정은 **개발2팀(레거시/운영) 주관**이며, 소통관 **서민지**가 접수한다. **각 단계마다 담당 페르소나를 노출하라.**

## 1단계: [PM팀·서민지] 접수 — T4 문서 작성

$ARGUMENTS 를 아래 T4 구조로 정리해 출력하라. 머리말은 4필드만 사용 (TOOL_PREF 금지):

```
TYPE: BUGFIX
SCOPE: web
PRIORITY: <P0|P1|P2|P3 — 영향도 기준으로 판단>
TARGET_DATE: <ASAP가 기본. P0/P1이면 SLA 명시: P0 머지 4시간, P1 머지 24시간>

## 1. 증상 (객관)
## 2. 재현 절차 (번호 매김 → 기대/실제)
## 3. 환경 (플랫폼·버전·SHA — git rev-parse HEAD로 확인)
## 4. 로그·스크린샷
## 5. 영향 (사용자 비율·역할별: USER/HOSPITAL/SALES_MANAGER/ADMIN)
```

재현 절차가 보고에 없으면 코드 분석으로 추정 재현 절차를 세우되 `(추정)` 표시. 재현 자체가 판정 불가하면 사용자에게 질문한다.

## 2단계: [개발2팀] 재현 확인

- 관련 코드 경로 탐색 (`src/app/`, `src/lib/`, API 라우트)
- 가능하면 실제 재현: `docker-compose logs -f app` 로그 확인, `docker exec ultra_app ...`로 검증, 필요 시 Adminer/psql로 DB 상태 확인
- 재현 성공/실패와 관찰 결과를 기록

## 3단계: [개발2팀] 원인 분석 — 5-Why RCA

증상에서 근본 원인까지 5단계 Why를 코드 근거(파일:라인)와 함께 작성:

```
Why 1: 왜 <증상>이 발생하는가? → <직접 원인 + 코드 근거>
Why 2: 왜 그런가? → ...
Why 3~5: (근본 원인에 도달할 때까지, 5개 미만으로 도달하면 도달 지점에서 종료 명시)
근본 원인(RCA): <한 문장>
```

## 4단계: [개발2팀] 최소 수정

- **근본 원인만 고치는 최소 diff**로 수정. 리팩토링·스타일 정리는 이 커밋에 섞지 않는다 (필요하면 별도 후속 제안)
- 수정 전후 동작 차이를 명시

## 5단계: [개발2팀 + QA팀] 회귀 확인

- 재현 절차를 다시 수행해 수정 확인 (기대 = 실제)
- 주변 기능 회귀 확인: 같은 파일/모듈을 쓰는 다른 경로 최소 2곳 점검
- `docker exec ultra_app npm run lint` + `docker exec ultra_app npx tsc --noEmit` 통과 확인
- **동일 클래스 버그 탐색**: 같은 패턴의 코드가 다른 곳에도 있는지 grep으로 검색해 발견 시 보고 (수정은 사용자 승인 후)

## 6단계: [PM팀·정대훈] 일관성 검토

- 수정 코드의 컨벤션/패턴 준수 확인. DB 관련 수정이면 윤성호/배지영 검토 추가

## 완료 보고

```
## 완료 보고
- RCA 요약: (한 문장)
- 수정 파일: (절대경로 + 변경 요지)
- 회귀 확인 결과: (재현 재수행 결과, lint/tsc 결과)
- 동일 클래스 탐색 결과: (발견 N건 / 없음)
- 골든 케이스 승격 후보: (이 버그의 재현 절차를 회귀 테스트 케이스로 제안)

## 참여 페르소나 및 빈도
(표 형식)
```

커밋은 사용자 요청 시에만, 컨벤션 `[fix] 설명` 준수.
