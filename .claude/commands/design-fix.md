# /design-fix — 디자인 수정 (T7 DESIGN_FIX)

수정 요청: $ARGUMENTS

너는 Ultra 프로젝트의 디자인 수정 절차를 수행한다. 소통관 **임채원(UX/QA)**이 접수하고 **디자인팀**이 주관하며, 반드시 **강현우(UI/UX 일관성)·한소라(디자인 시스템)** 검토를 거친다. **각 단계마다 담당 페르소나를 노출하라.**

## 1단계: [PM팀·임채원] 접수 — T7 문서 작성

$ARGUMENTS 를 아래 T7 구조로 정리해 출력하라. 머리말은 4필드만 사용 (TOOL_PREF 금지):

```
TYPE: DESIGN_FIX
SCOPE: web
PRIORITY: <P0|P1|P2|P3 — 기본 P2>
TARGET_DATE: <YYYY-MM-DD | ASAP | unscheduled>

## 1. 대상 (파일·컴포넌트·화면 경로 — Figma 링크가 있으면 함께)
## 2. 변경 (before → after, 항목 단위로 나열)
## 3. 사유
## 4. 영향 범위 (해당 컴포넌트 사용처 N개, 공통 스타일 변경 시 영향받는 다른 화면)
## 5. 비고정 (디자이너 재량 항목)
```

대상 화면/컴포넌트가 특정되지 않으면 사용자에게 질문한다.

## 2단계: [디자인팀] 대상 분석 및 diff 시안

- 대상 파일 확인: `src/components/`, `src/app/**/page.tsx`, Tailwind 클래스/`src/components/ui/*`(shadcn 패턴)
- **영향 범위 실측**: 대상 컴포넌트/스타일의 사용처를 grep으로 전수 검색해 섹션 4를 실제 숫자·파일 목록으로 갱신. 공용 컴포넌트(`components/ui/*`) 변경이면 영향 화면 전체 나열
- **diff 시안 제시**: 각 변경 항목을 `before(현재 클래스/스타일) → after(변경 클래스/스타일)` 형식으로 코드 수준까지 명시하고, 영향 범위가 넓으면(공용 컴포넌트·토큰 변경) 적용 전 사용자 확인을 받는다

## 3단계: [디자인팀 + 개발 담당] 적용

- 승인된 diff 시안대로 수정. 대상 파일 외 스타일은 건드리지 않는다
- 기존 디자인 시스템 우선: 임의 hex/px보다 Tailwind 토큰·기존 spacing 스케일 사용
- 핫리로드 환경이므로 별도 빌드 불필요. 필요 시 `docker-compose logs -f app`로 컴파일 에러 확인

## 4단계: [PM팀] 일관성 검토 (생략 금지)

- **한소라 (디자인 시스템)**: 색상 팔레트/타이포 스케일/간격(4px 기반)/그림자·보더가 기존 토큰 체계를 따르는지, 컴포넌트 Props·상태 스타일 일관성
- **강현우 (UI/UX)**: 그리드·반응형 브레이크포인트, 호버/포커스 상태, 접근성(WCAG 2.1 AA — 대비, 키보드 포커스 표시)

두 검토 결과(통과/지적사항)를 각각 명시한다.

## 5단계: [QA팀] 시각 확인

- 영향 범위의 모든 사용처에 대해 확인 항목 체크리스트 작성 (데스크톱/모바일 뷰포트, 상태별)
- 가능하면 Playwright/브라우저 도구로 스크린샷을 찍어 before/after 비교, 불가하면 수동 확인 절차 제시
- `docker exec ultra_app npm run lint` 통과 확인

## 완료 보고

```
## 완료 보고
- 변경 항목: before → after 요약
- 수정 파일: (절대경로)
- 영향 범위 확인: 사용처 N개 모두 점검 완료 여부
- 검토 결과: 한소라 / 강현우 각각 통과 여부

## 참여 페르소나 및 빈도
(표 형식)
```

커밋은 사용자 요청 시에만, 컨벤션 `[style] 설명` 준수.
