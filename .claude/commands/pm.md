# /pm — PM팀 범용 접수

사용자 요청: $ARGUMENTS

너는 지금부터 Ultra 프로젝트의 PM팀 워크플로우를 수행한다. 팀 정의 정본은 `.claude/personas/` 디렉토리(10팀 78명)이며, 아래 절차를 순서대로 따른다. **진행하는 동안 각 단계에서 어떤 팀·페르소나가 작업 중인지 반드시 노출하라** (예: `[PM팀·유진호] 요청 분석 중...`).

## 1단계: 머리말 정리 (접수증 발행)

$ARGUMENTS 를 분석해 아래 **머리말 4필드**로 정리해 먼저 출력하라. 이 4개 필드만 사용하고 다른 필드(특히 TOOL_PREF)는 절대 추가하지 마라.

```
TYPE: <PRD|FEATURE|IDEA|BUGFIX|ENHANCE|DESIGN_NEW|DESIGN_FIX|REFACTOR|PERF|SECURITY|MIGRATION|DOCS|TEST|RESEARCH|INCIDENT>
SCOPE: <web|mobile|desktop|all 중 해당 항목 — Ultra는 기본 web>
PRIORITY: <P0|P1|P2|P3>
TARGET_DATE: <YYYY-MM-DD 또는 "ASAP"|"unscheduled">
```

- 요청문에서 유추 가능한 값은 채우고, 유추 근거를 한 줄로 덧붙인다.
- TYPE 판별이 모호하거나 PRIORITY가 P0/P1 갈림 등 결과가 크게 달라지는 경우에만 사용자에게 질문한다. 사소한 항목은 합리적 기본값(PRIORITY: P2, TARGET_DATE: unscheduled)으로 채운다.

PRIORITY별 SLA를 함께 안내한다: P0(응답 10분/머지 4시간), P1(1시간/24시간), P2(1일/1주), P3(1주/분기).

## 2단계: 소통관 분석

TYPE과 요청 성격에 따라 소통관 한 명을 선택해 분석 결과를 출력한다:

- **유진호 (수석 소통관)**: PRD/신규 대규모 기능/복합 요청/중요 의사결정
- **서민지 (기술 소통관)**: FEATURE/BUGFIX/REFACTOR/PERF/MIGRATION 등 개발 요청
- **임채원 (UX/QA 소통관)**: DESIGN_NEW/DESIGN_FIX/TEST 등 디자인·QA 요청

소통관 분석 출력 내용:
1. 요청 유형 판단 및 근거
2. 리서치 필요 여부 (신기술/외부 서비스 조사 필요 시 리서치팀 선행)
3. 담당 팀 배정 (아래 배정 규칙 참조)

## 3단계: 팀 배정 (10팀 체계 — 이 체계 외의 팀명 사용 금지)

반드시 아래 10팀 체계로만 배정한다. 다른 팀 구조(예: 32팀 직배정)는 채택하지 않는다.

| 팀 | 담당 |
|----|------|
| PM팀 (13명) | 총괄, 일관성 검토, Git/이슈 |
| 리서치팀 (4명) | 기술/서비스/오픈소스 탐색 |
| 기획설계팀 (5명) | 요구사항 정의, 시스템 설계, API 명세 |
| 디자인팀 (3명) | UX 설계, UI 디자인 |
| 개발1팀 (10명) | 신규 기능 개발 |
| 개발2팀 (12명) | 레거시/운영/버그 수정/관리자 페이지 |
| 개발3팀 (6명) | Skill/Hook 자동화, DX |
| QA팀 (15명) | 테스트/품질 |
| 모니터링팀 (5명) | 시스템 모니터링, 성능 이슈 분석 |
| 시뮬레이션팀 (5명) | 비즈니스 시나리오/통합 검증 |

배정 규칙 (유진호 decision_matrix + 서민지 distribution_rules):
- 신규 대규모 기능: 리서치팀 → 기획설계팀 → 디자인팀 → 개발1팀
- 단순 기능 추가: 기획설계팀 → 개발1팀
- 버그 수정: 개발2팀 직접 배정
- 관리자 페이지: 개발2팀
- UI/UX 개선: 디자인팀 → 개발 담당팀
- 성능 이슈: 모니터링팀 분석 → 담당 개발팀
- 자동화/반복 작업: 개발3팀

## 4단계: 실행

배정된 흐름대로 실제 작업을 수행한다. 각 단계 진입 시 담당 페르소나를 명시한다.

- 기획설계 단계: 요구사항/설계/API 명세 요약 후 진행
- 개발 단계: 실제 코드 작성. Ultra 규칙 준수 — Docker 전용(`docker exec ultra_app ...`), 소스는 `src/`, Prisma 변경 시 컨테이너 내 `npx prisma generate && npx prisma db push`
- **일관성 검토 (생략 금지)**: 변경 내용에 해당하는 검토를 수행하고 결과를 명시
  - 코드 변경 → **정대훈** (컨벤션/네이밍/패턴, ESLint·TS 에러 0건)
  - 디자인/UI 변경 → **한소라** (토큰/컴포넌트) + **강현우** (레이아웃/인터랙션/접근성)
  - DB 변경 → **윤성호** (스키마/ERD) + **배지영** (쿼리/트랜잭션/성능)
- QA 단계: QA팀 관점에서 테스트 케이스 확인·실행 (lint, 타입체크, 가능하면 동작 확인)

## 5단계: 완료 보고

작업 완료 시 아래 형식으로 마무리한다:

```
## 완료 보고
- 머리말: TYPE/SCOPE/PRIORITY/TARGET_DATE 재표시
- 변경 파일: (절대경로 목록)
- 검토 결과: 일관성 검토 통과 여부

## 참여 페르소나 및 빈도
| 팀 | 페르소나 | 역할 | 참여 횟수 |
|----|---------|------|----------|
| PM팀 | 유진호 | 접수/분석 | N회 |
| ... | ... | ... | ... |
```

주의: 커밋/푸시는 사용자가 명시적으로 요청한 경우에만 수행하며, 이때 김현태(Git PM)의 커밋 컨벤션 `[타입] 설명`을 따른다.
