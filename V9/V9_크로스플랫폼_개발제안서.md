# V9 크로스 플랫폼 개발 제안서 (Web / iOS / Android / macOS / Windows + Watch / Smart Glasses)

> 부속 문서. 본문 = `V9_업그레이드_제안서.md`.
> V7 페르소나·에이전트·공유DB 인프라 위에서 **7개 플랫폼 클러스터를 단일 코드베이스 + 단일 데이터 모델**로 운영하기 위한 설계.
> 플랫폼 클러스터: Web · Mobile(iOS/Android) · Desktop(macOS/Windows) · **Wearable(watchOS/Wear OS)** · **Smart Glasses(visionOS/Android XR/Quest 등)**

---

## 0. 한 줄 결론

**Monorepo + 공유 도메인 코어 + 플랫폼별 얇은 셸**.
- 핵심 비즈니스 로직·DB 스키마·동기화 엔진은 **TypeScript 단일 패키지**
- UI는 **React Native (iOS/Android) + Web(React) + Tauri 2.0 (macOS/Windows)** — 모두 React 생태 공유
- **Wearable·Smart Glasses는 네이티브가 필수** (RN의 wearable/XR 지원 불충분) → Swift/Kotlin 컴패니언 모듈 + 공유 코어를 **Protocol Buffers 스키마**로 연결
- 백엔드는 V7 공유DB(PostgreSQL) + 동기화 게이트웨이(ElectricSQL 또는 자체 CRDT) + **컴패니언 디바이스 페어링 게이트**

## 1. 스택 선택 (대안 비교 후 결정)

### 1.1 후보 비교

| 옵션 | 공유율 | 학습곡선 | 성능/네이티브 감 | 결정 |
|---|---|---|---|---|
| **A. RN(Mobile) + React(Web) + Tauri(Desktop)** | 70-80% | 중 | 높음(Desktop은 OS WebView) | **채택** |
| B. Flutter 전 플랫폼 | 95% | 중 | 매우 높음 | Web SEO·접근성 약함, V7 React 생태 단절 |
| C. KMP(코어) + Compose Multiplatform | 80% | 높음 | 매우 높음 | iOS UI 성숙도 낮음, 팀 학습비용↑ |
| D. Electron(Desktop) | 60% | 낮음 | 메모리 큼 | Tauri 대비 번들 5-10배 |
| E. PWA만 | 100% | 낮음 | 네이티브 기능 제한 | 푸시·생체인증·백그라운드 제약 |

**결정 사유**:
- V7 페르소나·에이전트가 이미 TS/JS 친화적 (MCP TS SDK)
- Tauri 2.0이 mobile target도 지원하지만 안정성은 RN이 우위 → 모바일은 RN
- Desktop은 Tauri로 번들 작게 + Rust 사이드카로 네이티브 기능

### 1.2 최종 스택


## 5. DB 구축 (서버 + 디바이스 듀얼 스택)

### 5.1 서버 (V7 공유DB 확장)
- **PostgreSQL 16 + pgvector** (V7 본문 A1과 동일)
- 신규 테이블:
  ```sql
  -- 멀티 디바이스 동기화용
  CREATE TABLE devices (
    id uuid PRIMARY KEY,
    user_id uuid REFERENCES users(id),
    platform text CHECK (platform IN ('web','ios','android','macos','windows')),
    last_seen timestamptz,
    push_token text,
    public_key text  -- E2E 암호화용
  );

  CREATE TABLE sync_oplog (
    id bigserial PRIMARY KEY,
    user_id uuid,
    entity text, entity_id uuid,
    op text CHECK (op IN ('insert','update','delete')),
    payload jsonb,
    vector_clock jsonb,         -- 디바이스별 카운터
    server_ts timestamptz DEFAULT now(),
    origin_device uuid REFERENCES devices(id)
  );
  CREATE INDEX idx_oplog_user_ts ON sync_oplog(user_id, server_ts);
  ```
- **Row Level Security**: `user_id = auth.uid()` 정책 강제
- **Partitioning**: `sync_oplog`를 월 단위 파티션 (대용량 대비)

### 5.2 디바이스(로컬)
| 플랫폼 | 로컬 DB | KV | 파일 |
|---|---|---|---|
| iOS/Android | op-sqlite or WatermelonDB | MMKV | RNFS |
| Web | SQLite WASM(wa-sqlite) + OPFS | IndexedDB | Cache API |
| macOS/Windows | SQLite (Tauri sqlx) | Tauri Store | OS native FS |

**원칙**: 서버 스키마의 **부분 미러** + 자주 쓰는 인덱스만 유지 + 90일 LRU 제거.

### 5.3 마이그레이션
- 단일 진실원: `packages/db-schema` (Drizzle ORM)
- 서버 마이그레이션: `drizzle-kit push`
- 디바이스 마이그레이션: 앱 시작 시 버전 비교 → 점진적 ALTER
- **다운그레이드 금지** 원칙 (앱 강제 업데이트 + 서버 N-1 호환 정책)

## 6. 동기화 (Offline-First, Conflict-Aware)

### 6.1 패턴 선택
- **권장: PowerSync 또는 ElectricSQL** (PostgreSQL 직결, Phase 2에서 도입)
- 자체 구축 시: **oplog 기반 + 벡터 클럭 + 의미 단위 충돌해결**

### 6.2 동기화 흐름
```
[Device]                              [Sync Gateway]            [PostgreSQL]
  └ local write → SQLite + oplog
                ↘ WebSocket/HTTP3 push
                                       ├ 검증·권한·머지
                                       └ 영속 + 다른 디바이스 fan-out
  ← 변경 이벤트 stream ─────────────────┘
```

### 6.3 충돌 해결 전략 (엔티티별)
| 엔티티 | 전략 | 이유 |
|---|---|---|
| 텍스트 노트·문서 | **CRDT(Yjs)** | 동시 편집 보존 |
| 카운터·재고 | **OR-set or G-Counter** | 가환성 |
| 사용자 프로필 | **LWW(서버 ts)** | 단순 |
| 결제·트랜잭션 | **서버 단일 진실원** (디바이스 작성 금지) | 정합성 |
| 이미지·바이너리 | **content-addressed (SHA-256)** | 중복 제거 |

### 6.4 네트워크
- 우선순위 큐: foreground 작업 > background sync > prefetch
- 백오프: exponential + jitter
- 배터리 인식(Mobile): 저전력 모드에서는 batch 주기 ↑

### 6.5 실시간 채널
- Web/Desktop: WebSocket (Hono + ws)
- Mobile: WebSocket 우선, 백그라운드 시 푸시(silent push)로 wake-up

## 7. 보안 (플랫폼 통합)

### 7.1 인증·인가
- V7 본문 B1(JWT/OAuth2) 그대로 활용
- 모바일: **PKCE** + Authorization Code Flow, 토큰은 Keychain(iOS)/Keystore(Android)
- 데스크톱: OS 자격증명 저장소 (macOS Keychain, Windows DPAPI/Credential Manager)
- 웹: HttpOnly + Secure + SameSite=Lax 쿠키, BFF 패턴 권장

### 7.2 저장소 보안
| 항목 | 보호 |
|---|---|
| 토큰 | 플랫폼 보안 저장소 (절대 AsyncStorage/localStorage 금지) |
| 로컬 SQLite | SQLCipher 또는 OS 디스크 암호화 + 필드 레벨 암호화(민감 컬럼) |
| E2E 메시지 | libsodium / age, 디바이스별 공개키 등록 |
| 시크릿(API key 등) | 코드에 절대 포함 금지, EAS Secrets + Tauri 빌드 시 환경 주입 |

### 7.3 전송·앱 무결성
- TLS 1.3 + HSTS, **인증서 핀닝**(Mobile은 react-native-ssl-pinning)
- iOS **App Attest** + Android **Play Integrity** + Web **WebAuthn**(가능 시)
- Desktop 코드사인 검증 + Tauri Updater 서명 키 분리

### 7.4 권한 최소화
- 페르소나 RBAC(V7 B1)을 클라이언트 작업 권한과 동기화
- Mobile 권한(카메라·위치 등)은 사용 시점 요청 + 사유 다이얼로그

### 7.5 V7 Trust&Safety 연계
- 사용자 입력 → Trust&Safety 페르소나가 PII·유해 콘텐츠 1차 필터 → 서버 저장
- 자동 PII 마스킹(V7 B4) 동일 파이프라인 공유

### 7.6 감사·법규
- 감사 로그(V7 B2)를 디바이스 작업까지 확장 (origin_device 포함)
- GDPR/개인정보보호법: "내 데이터 내보내기·삭제" 엔드포인트 필수
- 어린이 사용 가능성 있으면 COPPA/연령 게이트

## 14. Wearable (Apple Watch · Wear OS) 전용 설계

### 14.1 스택 — 네이티브 강제
| 플랫폼 | UI | 통신 | DB | 비고 |
|---|---|---|---|---|
| **watchOS** | SwiftUI + WidgetKit(Complication) + ClockKit | `WatchConnectivity`(전송 큐/파일/applicationContext) | SwiftData or GRDB.swift | iOS 컴패니언 필수 |
| **Wear OS** | Jetpack Compose for Wear + Tiles + Complications | `Wearable Data Layer API` (DataClient/MessageClient/ChannelClient) | Room + DataStore | Android 컴패니언 필수(독립 앱 가능하지만 비권장) |

**RN/Flutter 제외 사유**: Wear OS는 Compose for Wear가 사실상 표준, watchOS는 RN 비공식 fork만 존재. 두 OS 모두 글랜서블 UX·배터리·Always-On Display 최적화가 네이티브 SDK 외엔 어렵다.

### 14.2 공유 코어 연결
- TypeScript 도메인 모델을 **Protobuf로 미러** → `swift-protobuf`(iOS/watchOS) + `protobuf-kotlin`(Android/Wear)
- 핵심 검증 로직은 Protobuf + 짧은 네이티브 검증기 (코어 풀 포팅은 비용 과다)
- 텍스트 컨텐츠·아이콘 자원은 공유 패키지(JSON/PNG)로 추출 후 빌드 시 복사

### 14.3 UX 패턴
- **글랜서블 우선**: 화면 1.5-2초 노출 가정, 한 화면 = 한 작업
- **Complication / Tiles**: 핵심 지표 1-2개 (예: 오늘 할 일 카운트, 다음 알림까지 시간)
- **음성 + 햅틱**: 양손 사용 어려울 때 Voice Input + 단계적 햅틱 패턴
- **Always-On**: 절전 모드용 단색·저주사 화면 별도 디자인
- **세션 단위 트래킹**: 운동·집중 등은 WorkoutKit(iOS) / Health Services(Wear) 사용

### 14.4 데이터·동기화
- 페어링 폰을 **1차 게이트웨이**로 사용 (워치 → 폰 → V7 서버)
- 직접 LTE/Wi-Fi 가능 모델: 핵심 작업만 직접 동기화 (예: SOS, 결제)
- 충돌해결: 폰-워치 간 LWW + `sync_oplog.origin_device`에 워치 ID 분리 기록
- 미디어·이미지: 워치엔 썸네일·텍스트만, 큰 자산은 폰으로

### 14.5 권한·센서
- HealthKit(iOS) / Health Services(Wear): 심박·운동·수면 — 사용 시점 요청
- 위치는 사용 패턴 따라 `WhenInUse` 우선, Always는 정당화 필수
- 마이크·카메라(워치는 카메라 없음)·NFC(결제)는 별도 사용 동의

### 14.6 테스트
- **시뮬레이터**: Apple Watch Simulator, Wear OS Emulator (Round/Square/Long 폼팩터)
- **실기 필수**: Always-On·배터리·햅틱·페어링 끊김은 시뮬레이션 한계 명확
- **E2E**: XCUITest(watchOS), UiAutomator(Wear) — 둘 다 페어 디바이스 동시 제어 필요
- **저전력·연결 시나리오**: 비행기 모드 토글, 페어 끊김 후 큐 적재 확인을 골든 케이스화

### 14.7 빌드·서명·스토어
- watchOS: Xcode + iOS 앱과 동일 번들에 watch extension 포함 → App Store Connect 단일 제출
- Wear OS: 독립 APK·AAB 또는 폰 앱 내 모듈 (현재는 독립 등록 권장) → Play Console "Wear OS" 카테고리

### 14.8 보안
- 페어 토큰 회전 + BLE 페어링 보안(중간자 차단)
- 워치-폰 메시지 서명(Ed25519) — V7 보안 키 인프라 재사용
- 분실 모드: 원격 와이프, 로컬 데이터 휘발(키만 폐기로 사실상 와이프)

## 15. Smart Glasses (visionOS · Android XR · Quest · 페어형 글래스) 전용 설계

### 15.1 카테고리 구분 — 매우 다른 디바이스를 한 단어로 묶지 말 것

| 분류 | 대표 디바이스 | OS / SDK | 컴퓨팅 | 컴패니언 |
|---|---|---|---|---|
| **A. Mixed Reality 헤드셋** | Apple Vision Pro | visionOS (SwiftUI + RealityKit) | 디바이스 자체 강력 | iPhone 선택적 |
| **B. Android XR 헤드셋** | Samsung Project Moohan, 향후 OEM | Android XR (Jetpack XR SDK) | 디바이스 강력 | Android 폰 |
| **C. OpenXR 헤드셋** | Meta Quest 3/3S, Pico | Horizon OS(Android 기반) / Pico OS, OpenXR | 디바이스 강력 | Meta 계정·앱 |
| **D. 페어형 스마트 글래스** | Ray-Ban Meta, Snap Spectacles(개발자판), XREAL Air | 페어 폰(iOS·Android) 앱 + 글래스 SDK | 글래스 약함, 폰이 주 컴퓨팅 | **필수** |
| **E. AR Cloud / WebXR** | 브라우저 기반 | WebXR Device API | 브라우저 | — |

**전략**: 카테고리별 **별도 앱 변형**을 인정. 코어 도메인만 공유.

### 15.2 스택 결정

| 카테고리 | UI/UX | 공유 코어 활용 | 추가 |
|---|---|---|---|
| A. visionOS | SwiftUI + RealityKit + ARKit | Protobuf로 도메인 | Volumetric 윈도우·Immersive Space 디자인 |
| B. Android XR | Jetpack Compose XR + ARCore | Protobuf로 도메인 | Spatial UI 가이드라인 준수 |
| C. Quest | **Unity 6 + XR Interaction Toolkit + OpenXR** (또는 Unreal) | C# 바인딩 또는 IPC | 오피스/도구 앱이면 React Native for Quest도 고려 |
| D. Ray-Ban Meta 등 | **Meta Wearables SDK** + RN 컴패니언 폰 앱 | 폰 앱이 V7 코어 그대로 사용 | 디바이스는 음성·미디어 위주 얇은 UX |
| E. WebXR | React + three.js / react-three-fiber + WebXR | 웹 패키지 그대로 | 진입장벽 낮음, 성능 한계 |

### 15.3 UX·인터랙션 원칙
- **시선(Gaze) + 핀치**가 visionOS 표준, **컨트롤러**가 Quest 표준 — UI를 둘 다 수용
- 텍스트 입력은 가상 키보드보다 **음성·받아쓰기** 우선
- 멀미 방지: 카메라 강제 이동 금지, 텔레포트·스냅 회전 사용
- **Spatial Audio**: 알림·피드백을 위치감 있는 사운드로
- **세이프티**: 가드 영역·물리적 환경 인식(passthrough)을 항상 보존

### 15.4 데이터·동기화
- 헤드셋(A·B·C): 폰 없이 직접 V7 서버와 동기화 — Web/Desktop과 동일 게이트웨이 사용 (OS 토큰 저장소만 변경)
- 페어형 글래스(D): **폰을 1차 게이트웨이**로 사용, 글래스→폰 BLE/USB-C → 폰→서버
- 비디오·LiDAR 등 대용량 센서 데이터는 **온디바이스 추론 후 메타데이터만 업로드** 원칙 (대역폭·프라이버시)

### 15.5 권한·프라이버시 (가장 민감)
- 카메라·시선·환경 메시(가구·얼굴 인식)는 **항상 사용자가 명시 동의**
- visionOS: ARKit 환경 데이터는 기본 비공개, 명시 권한만 통과
- Android XR: AndroidManifest의 XR 권한 + 런타임 권한
- Quest/페어형: 카메라 패스스루는 기록·전송 금지 정책 (Meta 정책 위반 시 거절)
- V7 Trust&Safety 페르소나가 XR 콘텐츠 가이드라인(괴롭힘·괴이한 콘텐츠 등) 사전 검토

### 15.6 테스트
- **시뮬레이터**: Vision Pro Simulator(Mac Apple Silicon 한정), Android XR Emulator, Meta XR Simulator(Unity Editor)
- **시뮬레이터 한계**: 6DoF 추적·핸드·시선은 실기 필수
- 자동화: 일반 E2E 도구가 약함 → **시나리오 스크립트 + 골든 스크린샷**(visionOS는 RealityKit 캡처 사용)
- 휴먼 테스트가 핵심 → **휴먼 평가 골든케이스**(시나리오·합격기준·기록 양식)를 V7 evals에 별도 카테고리로 추가

### 15.7 빌드·서명·스토어
| 디바이스 | 빌드 | 스토어 | 비고 |
|---|---|---|---|
| Vision Pro | Xcode | App Store(visionOS 카테고리) | iOS 앱 호환 모드도 가능 |
| Android XR | Android Studio + XR Emulator | Play Store(XR 섹션) | 2026 시점 신생 카테고리 |
| Quest | Unity Build + Meta Quest Developer Hub | **Meta Horizon Store**(구 Oculus Store) + AppLab → Store 승격 | 정책 심사 까다로움 |
| 페어형 글래스 | iOS/Android 앱과 동일 | App Store / Play Store + 글래스 OEM 등록 | 디바이스 펌웨어 업데이트 별도 |

### 15.8 보안
- 헤드셋도 OS 보안 저장소 사용 (visionOS Keychain, Android Keystore)
- 페어형 글래스: 폰-글래스 BLE 페어링 인증서 + 회전, 글래스 분실 시 폰에서 원격 차단
- 환경 매시·카메라 프레임은 **저장 금지 기본**, 저장 필요 시 명시 동의 + 로컬 암호화

### 15.9 컴패니언 페어링 아키텍처 (Watch + Glasses 공통)
```
[Companion Device]                    [Pairing Service]              [V7 API]
  └ BLE/WiFi-Direct 페어링
                ↘ JWT(디바이스) 발급                ┐
                                       └ devices 등록 + 공개키 저장
  ← Spatial/Glanceable 데이터 push ─────┘                ↘ V7 sync_oplog
                                                          (origin_device=companion)
```
- `devices.platform`에 `watchos/wearos/visionos/android-xr/quest/glasses-pair` 추가
- 페어링 세션은 별도 짧은 수명 토큰 + 부모 디바이스 토큰과 체이닝

### 15.10 신규/확장 페르소나
| 페르소나 | 책임 |
|---|---|
| **Wearable팀** (Mobile Platform 산하) | 워치 OS·복잡도, 페어링, 헬스 정책 |
| **XR/Spatial팀** (신규) | visionOS·Android XR·Quest UX 규약, 멀미·세이프티 |
