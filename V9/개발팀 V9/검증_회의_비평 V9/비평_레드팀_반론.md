# V9 레드팀 비평·반론

> 작성일: 2026-06-27
> 입장: 적대적(adversarial). V9을 깨러 온 문서다. 잘 만든 점은 칭찬하지 않는다 — 그건 다른 문서의 일이다. 여기서는 "어떻게 실패할 수 있는가"만 본다.
> 형식: 각 항목 [비판] → [근거] → [심각도 상/중/하] → [V9 대응/완화책 또는 '미해결'].

---

## #1. 자율 루프의 환각 누적·은밀한 실패
- **[비판]** 루프가 틱마다 코드를 바꾸며 도는 동안, 작은 환각이 누적돼 "그럴듯하지만 틀린" 상태로 수렴할 수 있다. one-shot은 한 번 틀리면 사람이 보지만, 자율 루프는 **사람이 안 보는 사이** 틀린 방향으로 자기강화된다.
- **[근거]** 루프 품질은 베이스 모델이 아니라 루프·CHECKER 설계에서 난다는 것이 업계 합의다(DOER는 쉽고 CHECKER가 어렵다). CHECKER가 약하면 루프는 환각을 합격으로 굳힌다. ([mindstudio.ai](https://www.mindstudio.ai/blog/what-is-loop-engineering-ai-coding-agents))
- **[심각도] 상**
- **[대응]** STOP을 결정적 게이트(CI/테스트/타입/린트)에 묶고, REPORT(`loop_runs` + `loop-report-emit.sh`)로 매 틱 변경을 적립해 사후 추적. 단, "사후 추적"은 막은 게 아니라 본 것뿐 — **실시간 차단은 결정적 게이트가 잡는 범위에서만** 유효. 게이트가 못 잡는 의미적 오류는 **부분 미해결**.

## #2. grader도 LLM — 공모(collusion) 가능
- **[비판]** grade-revise의 grader가 LLM인 한, DOER와 같은 약점을 공유해 틀린 코드를 함께 합격시킬 수 있다. 자기채점의 고전적 실패.
- **[근거]** Performance Outcomes는 grader가 루브릭으로 채점하는 구조인데, grader가 DOER와 동계열이면 편향이 상관된다. ([claude.com/blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more))
- **[심각도] 상**
- **[대응]** (회의 결정) grader는 DOER와 **다른 모델**, **거부권만**(합격 단독 확정 금지), 결정적 게이트 우선. grader 오판 사례를 골든케이스로 회귀. **잔여 위험:** 다른 모델도 동일 학습 데이터 계보면 약점이 겹친다 → 정기 적대적 grader 테스트는 **미해결**.

## #3. 안드로이드 네이티브 ROI 의문 (팀 규모 대비)
- **[비판]** Kotlin/Compose 네이티브 트랙을 RN과 **병행**하면 빌드·CI·온콜 표면적이 두 배인데, 현재 설계는 RN 회수 없는 **순증**이다. 작은 팀이 두 스택을 1급으로 유지할 수 있는가.
- **[근거]** 회의에서 Android Native팀이 "지금은 순증에 가깝다"고 인정. 크로스플랫폼 7종을 이미 RN으로 떠받치는 상황.
- **[심각도] 상**
- **[대응]** (회의 결정) 네이티브 트랙은 **수요 게이트** 통과 시에만 active, 기본은 dormant(자산만 적재, CI/온콜 미가동). **잔여 위험:** "네이티브 전용 수요"의 판정 기준·주체 미합의 → ROI 분쟁 소지, **부분 미해결**.

## #4. BUDGET 우회
- **[비판]** 루프 단위 BUDGET 캡은 에이전트가 SCOPE를 넓혀 새 루프를 띄우거나 서브에이전트에 위임하면 우회될 수 있다. "캡이 있다"가 "캡을 못 넘는다"를 뜻하지 않는다.
- **[근거]** Dynamic Workflows의 fan-out 특성상 위임 체인이 길어지면 누적 비용 추적이 어려움. ([code.claude.com/docs — Sub-agents](https://code.claude.com/docs/en/sub-agents))
- **[심각도] 상**
- **[대응]** 세션·일 **누적 캡** + `loop-budget-guard` 감시로 SCOPE 재기동 우회 차단. **잔여 위험:** 위임 체인(서브에이전트가 또 서브에이전트)을 통한 우회를 전부 막았는지 미검증 → **부분 미해결**(회의 미해결 #2).

## #5. 신규 팀·페르소나 과다 → 컨텍스트 오염
- **[비판]** 31팀 + 에이전트/스킬/훅/eval이 한꺼번에 컨텍스트에 노출되면 신호 대 잡음이 나빠져, 모델이 무관한 페르소나 지식을 끌어와 오답을 낸다. "팀이 많다 = 능력이 크다"가 아니다.
- **[근거]** 점진적 공개는 라우팅이 정확할 때만 이득. 신규 팀(루프엔지니어/Android Native/OnDevice AI)이 기존 경계와 겹침.
- **[심각도] 중**
- **[대응]** skills 점진적 공개 + 신규 팀 라우팅 경계를 eval로 고정 + 항상로드 금지. **잔여 위험:** 라우터 오분류 시 오염은 오히려 증폭. 오염 측정 지표는 신설 예정(미배포).

## #6. 드롭인 최적화가 기존 레포 설정 덮어쓸 위험
- **[비판]** "V9을 현재 개발에 맞게 최적화" 한 줄 요청으로 드롭인 적용 시, 기존 `.claude/settings.json`·hooks·CI를 덮어쓰면 사용자 설정이 소실된다. 편의가 곧 파괴력.
- **[근거]** 드롭인은 본질적으로 파일 쓰기 작업이며, 충돌 처리 정책이 없으면 마지막 쓴 쪽이 이긴다.
- **[심각도] 상**
- **[대응]** (회의 결정) 드라이런 diff → 병합/백업 → PR 리뷰 3단, 자동 덮어쓰기 금지, 드롭인을 SCOPE 한정 루프로 명세. 비교적 잘 막힘. **잔여 위험:** 반복 충돌 시 운영 피로 → 정책 보강 후속.

## #7. eval 골든케이스가 루프 "행동"까지 못 잡는다
- **[비판]** 기존 eval은 입력→출력(결과물)의 회귀에 강하지만, 루프의 **과정**(몇 틱 돌았나, BUDGET을 어떻게 썼나, STOP이 거짓 완료였나, 우회했나)은 결과만 봐서 잡기 어렵다. 결과가 우연히 맞아도 루프 행동은 위험할 수 있다.
- **[근거]** `.claude/evals/loop/`가 존재하나 현재 비어 있음(스캐폴딩 단계). 골든케이스 패러다임은 산출물 검증 중심.
- **[심각도] 중**
- **[대응]** loop eval은 산출물이 아니라 **루프 trace**(틱 수·예산 사용·STOP 사유·SCOPE 이탈)를 검증하도록 설계해야 함. 현재 **미구현(비어 있음)** → **미해결**.

## #8. 온디바이스 AI 디바이스 파편화·무음 폴백
- **[비판]** Gemini Nano 4를 못 돌리는 기기에서 자동 서버 폴백이 일어나면, 사용자가 모르는 사이 데이터가 기기를 떠난다. "온디바이스=프라이버시"라는 마케팅이 폴백에서 무너진다.
- **[근거]** 온디바이스는 디폴트일 뿐 보장이 아니며, 파편화된 기기군에서 폴백은 불가피. ([developer.android.com/studio/gemini](https://developer.android.com/studio/gemini))
- **[심각도] 중**
- **[대응]** (회의 결정) **무음 서버 폴백 금지**(비활성 또는 명시 동의), 온디바이스 출력 로컬 보존 기본, 폴백 경로를 platform eval로 회귀. 비교적 잘 막힘.

## #9. A2A 토픽 폭증
- **[비판]** 팀이 31개로 늘면 에이전트 간(A2A) 메시지 토픽이 조합적으로 늘어 관찰성·디버깅이 어려워지고, 잡음 토픽이 실제 신호를 묻는다.
- **[근거]** 신규 3팀 추가로 토픽 생성 주체가 증가. 공유DB운영팀이 회의에서 별도 관리 필요성 지적.
- **[심각도] 중**
- **[대응]** A2A 토픽 상한·정리(retention) 정책 수립 예정. 현재 **정책 미배포** → **부분 미해결**.

## #10. 한글 폴더명 + 공백 경로의 스크립트 취약성
- **[비판]** 루트 경로에 `개발팀 V9`, `검증_회의_비평 V9`처럼 **공백·한글**이 섞여 있다. 인용을 빠뜨린 셸 스크립트(hook·드롭인·install)는 경로가 단어 단위로 쪼개져 오작동하거나 엉뚱한 파일을 건드린다. Dropbox 동기화 경로라 클라우드 지연·부분 동기화까지 겹친다.
- **[근거]** hook 다수가 `.sh` 스크립트(`pre-commit-typecheck.sh`, `loop-budget-cap.sh` 등). 공백/유니코드 경로는 셸에서 고전적 깨짐 원인.
- **[심각도] 중**
- **[대응]** 모든 스크립트의 경로 변수 **이중 인용** 의무화 + 경로 인용 회귀 테스트. Dropbox 동기화 지연은 쓰기 실패 시 재시도로 완화. 현재 인용 안전성 **전수 점검 미완** → **부분 미해결**.

## #11. "결정적 hooks"라는 안전 가정의 과신
- **[비판]** V9 안전 설계의 토대가 "hooks는 결정적·환각 불가"인데, 이는 **훅 스크립트 자체가 옳고, 항상 호출되며, 우회 불가일 때만** 성립한다. 훅을 건너뛰는 경로(예: 훅이 안 걸리는 도구 호출)가 하나라도 있으면 BUDGET/STOP 보장이 통째로 약해진다.
- **[근거]** "결정적"은 메커니즘의 속성이지 커버리지의 보장이 아니다. ([claude.com/blog](https://claude.com/blog/steering-claude-code-skills-hooks-rules-subagents-and-more))
- **[심각도] 상**
- **[대응]** 훅 커버리지(어떤 이벤트가 훅에 걸리고 안 걸리는지) 전수 매핑 + 미커버 경로 차단 필요. 현재 **커버리지 매핑 미완** → **미해결**.

## #12. 거짓 완료(false done) — STOP의 자기보고 신뢰
- **[비판]** `/goal` 류 루프는 "조건 충족"을 에이전트가 판단해 멈춘다. 에이전트가 "다 됐다"고 **자기보고**하면, 실제로는 미완인데 멈출 수 있다.
- **[근거]** goal 루프는 가장 강력하면서 가장 자주 오용되는 유형으로 평가됨. ([the-ai-corner.com](https://www.the-ai-corner.com/p/loop-engineering-coding-agents-2026))
- **[심각도] 상**
- **[대응]** STOP을 자기보고가 아니라 **외부 검증 가능 조건**(테스트 통과·CI 그린 등)으로만 정의(`완료조건_가이드.md`의 거짓 완료 방지). 결정적 게이트가 닿는 범위에서 유효 — 의미적 완성도는 **부분 미해결**.

## 그럼에도 채택해야 하는 이유 (3줄)
1. one-shot 프롬프팅은 다단계·대규모 작업에서 한계가 분명하고, 루프 엔지니어링은 Claude Code 2026 네이티브 기능(subagents·`/goal`·hooks)과 정합해 **사람의 반복 노동을 실제로 줄인다**.
2. V9은 자율성을 무제한으로 풀지 않고 BUDGET/STOP/사람 게이트·결정적 게이트로 **통제된 자율성**으로 가두는 설계 의지를 갖고 있다(잔여 위험은 있으나 방향은 옳다).
3. 안드로이드 네이티브·온디바이스 AI는 "전부 전환"이 아니라 **dormant 수요 게이트** 모델이라, 채택 자체가 즉각적 비용 폭증을 강제하지 않는다(켤 때만 비용).

## 채택 전 반드시 막아야 할 Top 3 리스크
1. **BUDGET·무한루프 우회 (#1·#4·#11).** 누적 캡 + 위임 체인 차단 + 훅 커버리지 전수 매핑이 끝나기 전에는 자율 변경 모드를 켜지 말 것. (켜되 제안 모드로만.)
2. **grader 공모·거짓 완료 (#2·#12).** grader 거부권 한정 + 결정적 게이트 우선 + STOP 외부검증화가 적용되기 전에는 grade-revise 결과를 머지로 자동 흘리지 말 것.
3. **드롭인 덮어쓰기 + 경로 취약성 (#6·#10).** 드라이런/백업/PR 3단 + 경로 이중 인용 회귀가 갖춰지기 전에는 드롭인 자동 적용 금지. 남의 레포 설정 1회 파괴가 신뢰를 통째로 깬다.

## #13. REFLECT 메모리 오염 — 틀린 교훈의 자기강화
- **[비판]** `loop_lessons`에 적힌 교훈이 틀렸거나 과적합이면, 재주입될수록 잘못된 행동이 강화된다. "기억"이 좋은 교훈만 기억한다는 보장은 없고, Reflexion의 자기성찰은 자기합리화로 변질될 수 있다.
- **[근거]** 교훈을 쓰는 주체가 LLM(`loop-reflector`)이라 grader 공모(#2)와 같은 계열 위험. 오답에서 "그럴듯한 교훈"을 뽑으면 오염이 누적된다.
- **[심각도] 상**
- **[대응]** 교훈은 행동가능·일반화로 제한, `outcome_delta`로 적용 효과를 측정해 무효 교훈 폐기, `reuse_count`만으로 신뢰하지 않음. **잔여 위험:** 효과 측정이 느리고 노이즈가 큼, 초기 교훈 품질 게이트 미비 → **부분 미해결**.

## #14. 무진행 오판 — 개선 중인데 조기 종료(또는 그 반대)
- **[비판]** "지표 N tick 무변화 → 정지"는 깊은 리팩토링 중 일시적 정체(곧 큰 개선)를 죽일 수 있다. 반대로 지표가 미세하게만 흔들리면 영원히 안 멈춘다.
- **[근거]** 단일 지표 델타는 비선형 수렴을 못 본다. 무진행 임계(N)는 작업마다 다른데 기본값(3)은 임의적.
- **[심각도] 중**
- **[대응]** 무진행은 STOP의 한 OR 조건일 뿐(상한·목표와 병행), 임계는 패턴/작업별 튜닝, 사람 게이트로 조기 종료 재검토. **잔여 위험:** 작업별 적정 N의 근거 데이터 부족 → `loop_runs` 누적 전까지 경험칙 의존, **부분 미해결**.

## #15. 컨텍스트 압축 유실 + 하네스 개념 과적재
