# 루프엔지니어링 방법론 (V9 본편)

> "이제 에이전트에게 프롬프트하지 말고, 에이전트를 프롬프트하는 루프를 설계하라."
> V9 한 줄 진화: **루프를 '하네스(harness)' 안에 넣어, 스스로 컨텍스트를 관리하고(CONTEXT) · 진전을 감지하며(PROGRESS) · 교훈을 기억하는(REFLECT) 루프로 끌어올린다.**

## 0. V8 → V9 무엇이 달라졌나 (요약)
V8은 루프를 **6요소(TRIGGER/SCOPE/ACTION/BUDGET/STOP/REPORT)** 로 정식화했다. V9은 이를 보존하면서 2026년 현장 표준이 된 다음 4가지를 1급 시민으로 끌어올린다.

| V9 신규 | 한 줄 | 닫는 갭 |
|---|---|---|
| **하네스 엔지니어링 관점** | 루프는 더 큰 "에이전트 하네스(제어판)"의 일부 — 5계층으로 배치 | 루프만 잘 짜도 도구/메모리/가드레일이 없으면 무너짐 |
| **3 운영 규율** `CONTEXT·PROGRESS·REFLECT` | 6요소(무엇을)에 더해 **어떻게 오래 잘 도는가**를 규정 | 컨텍스트 폭주·헛도는 루프·같은 실수 반복 |
| **루프 패턴 라이브러리** | ReAct/Plan-Execute/Evaluator-Optimizer/Reflexion/fan-out/grade-revise를 골라 쓰기 | "어떤 루프 형태를 쓸지" 임의 선택 |
| **`/goal` · 오케스트레이션 시대 매핑** | Claude Code `/goal`(완료조건)·Anthropic 2026 보고서의 control-before-autonomy 사다리 | 장시간·다중에이전트 자율의 안전 단계가 불명확 |

신규 자산: 에이전트 `loop-reflector`, 훅 `loop-no-progress-check.sh`·`loop-context-compact.sh`, 스킬 `loop-reflect`·`loop-pattern-select`, eval `no-progress-stop`·`reflection-memory`·`context-compaction`, DB `010_loop_lessons.sql`, 문서 `루프_패턴_라이브러리.md`·`하네스_엔지니어링_가이드.md`.

## 1. 정의
**루프 엔지니어링(Loop Engineering)** = AI 코딩 에이전트가 "계획 → 코드변경 → 결과관찰 → 수정"을 반복하는 피드백 루프를 **설계·운영·개선**하는 분야다. 단발성 지시(one-shot 프롬프트)를 던지고 결과를 받는 방식이 아니라, **언제 돌고(트리거) / 어디까지 손대고(범위) / 무엇을 하고(행동) / 얼마를 쓰고(예산) / 언제 멈추고(정지) / 누구에게 보고할지(보고)** 를 미리 규정한 자율 반복 시스템을 만든다.

핵심 전환: 작업자는 "정답을 한 번에 뽑는 프롬프트"를 쥐어짜는 대신 **"틀려도 스스로 고쳐 수렴하는 루프"** 를 설계한다. 2026년 6월, Peter Steinberger·Boris Cherny·Addy Osmani가 동시에 같은 전환을 지목했다 — **"작업의 단위는 더 이상 프롬프트가 아니라 루프다."**[^1][^2][^3]

## 2. 성숙도 3단계: 프롬프트 → 컨텍스트 → 하네스 엔지니어링
2026년의 AI 엔지니어링은 세 단계로 성숙했다. 루프 엔지니어링은 3단계(하네스)의 심장이다.[^5]

| 단계 | 질문 | 다루는 것 |
|---|---|---|
| **프롬프트 엔지니어링** | "어떻게 물어볼까" | 한 번의 지시 품질 |
| **컨텍스트 엔지니어링** | "무엇을 보여줄까" | 모델이 보는 정보(검색·요약·상태) |
| **하네스 엔지니어링 (2026)** | "어떤 환경에서 돌릴까" | 도구·검증루프·메모리·가드레일·관찰성으로 **모델을 신뢰 가능한 자율 에이전트로** |

> 루프는 하네스의 일부다. 좋은 루프라도 도구·메모리·가드레일·관찰성이 없으면 무너진다. 5계층 배치는 `하네스_엔지니어링_가이드.md` 참조.

## 3. 진화 계보: ReAct → 멀티스텝 에이전트 → 루프 엔지니어링
| 세대 | 핵심 | 한계 |
|---|---|---|
| **ReAct** (Reason+Act) | 추론과 도구 호출을 번갈아. 한 작업 안에서 생각하고 행동 | 작업 경계·정지·예산 개념이 없음 |
| **멀티스텝 에이전트** | 계획→실행→관찰을 여러 턴 반복, 도구 다수 사용 | 언제 멈출지·얼마 쓸지·누가 채점할지 임의적, 사람이 계속 개입 |
| **루프 엔지니어링 (2026)** | 루프 자체를 **명세(6요소)+운영규율(3)** 로 두고 트리거·예산·정지·채점·기억·보고를 1급 시민으로 설계 | (현 단계) — 무한루프·비용폭발·컨텍스트 폭주를 안전장치로 관리 |

요지: ReAct가 "한 작업 안의 루프"였다면, 루프 엔지니어링은 **"작업을 둘러싼 루프"** 를 공학적으로 다룬다. 구체적 루프 형태(패턴) 선택은 `루프_패턴_라이브러리.md`.[^2]

## 4. 루프 해부도 — 6요소 (구조)
모든 루프는 아래 6요소로 분해된다. 하나라도 비면 위험한 루프다.

### TRIGGER (언제 도는가)
| 항목 | 내용 |
|---|---|
| 정의 | 루프 한 tick(반복)이 시작되는 조건 |
| 예시 | 15분마다 / PR 코멘트 달릴 때 / CI 실패 이벤트 / `errors.new` 발행 시 |
| 안티패턴 | 트리거 없이 "항상 돌기" → 비용 폭발 |

### SCOPE (어디까지 손대는가)
| 항목 | 내용 |
|---|---|
| 정의 | 루프가 건드릴 수 있는 대상의 경계 |
| 예시 | 내가 연 PR만 / repo `flipbook`만 / `src/payments/**` 디렉터리만 / env:dev |
| 안티패턴 | 범위 무제한 → 의도치 않은 파일/레포 변경 |

### ACTION (무엇을 하는가)
| 항목 | 내용 |
|---|---|
| 정의 | 각 tick에서 에이전트가 수행하는 행동 |
| 예시 | 테스트 실행 / lint 자동수정 / 리뷰 코멘트 응답 / 의존성 업그레이드 PR |
| 안티패턴 | 행동이 모호("개선해줘") → 수렴하지 않음 |

### BUDGET (얼마를 쓰는가)
| 항목 | 내용 |
|---|---|
| 정의 | tick당·루프 전체의 자원 상한 |
| 예시 | tick당 서브에이전트 3개 / 50k 토큰 / 누적 $5 / tick당 최대 2분 |
| 안티패턴 | 상한 미설정 → 토큰·비용 폭주 |

### STOP (언제 멈추는가)
| 항목 | 내용 |
|---|---|
| 정의 | 루프 전체를 종료시키는 **결정적** 조건(OR 결합) |
| 예시 | 모든 PR green / 10회 반복 / $5 소진 / 60분 경과 / **무진행 3tick** / 사람 중단 |
| 안티패턴 | 정지조건이 주관적("충분히 좋아지면") → 무한루프 |

### REPORT (누구에게 보고하는가)
| 항목 | 내용 |
|---|---|
| 정의 | 종료(또는 중간) 시 요약과 수신처 |
| 예시 | Slack `#eng-bots`에 요약 / 공유DB `loop_runs` 적재 / PR 코멘트 |
| 안티패턴 | 보고 없음 → 무슨 일이 일어났는지 추적 불가 |

> 6요소 한 줄 요약: **언제(TRIGGER) · 어디(SCOPE) · 무엇(ACTION) · 얼마(BUDGET) · 끝(STOP) · 알림(REPORT)**

## 5. 운영 규율 — 3원칙 (V9 신규, "어떻게 오래 잘 도는가")
6요소가 루프의 **구조**라면, 아래 3규율은 루프가 길게 돌아도 무너지지 않게 하는 **운영 원리**다. 2026년 장시간 자율 루프의 실패는 대부분 이 셋의 부재에서 온다.

### ① CONTEXT — 컨텍스트 위생
긴 루프는 컨텍스트 창을 넘쳐 모델이 "패닉"하며 마무리를 서두르고 품질을 깎는다.[^5] 매 tick 다음을 강제한다.
- **압축/정리**: 직전 tick의 원시 로그·diff를 요약본으로 치환(raw dump 금지).
- **외부화(offload)**: 플랜·누적치(반복·토큰·비용)는 컨텍스트가 아니라 **스크립트 변수/`loop_runs`/환경변수**에 둔다(Dynamic Workflows 원칙과 동일).
- **선별 주입**: 다음 tick에 필요한 조각만 다시 넣는다(관련 lesson·실패 로그·대상 파일).
- 자산: 훅 `loop-context-compact.sh`(tick 경계에서 컨텍스트 예산 초과 시 요약/잘라내기), eval `context-compaction`.

### ② PROGRESS — 무진행 감지
반복은 도는데 결과가 나아지지 않으면 멈춰야 한다(헛도는 루프 = 비용만 소모). 상한(횟수·예산)과 별개로 **진전 신호**를 본다.
- **델타 판정**: 실패 테스트 수·커버리지·grader 점수가 N tick 연속 개선 없음 → `no_progress`.
- STOP에 `no_progress_ticks >= N`을 OR로 추가(기본 N=3).
- 자산: 훅 `loop-no-progress-check.sh`(결정적 판정, exit 1로 종료 신호), eval `no-progress-stop`.

### ③ REFLECT — 리플렉션 기억 (Reflexion)
실패에서 **언어로 된 교훈**을 뽑아 에피소드 메모리에 적고, 다음 tick·다음 루프 시작 시 관련 교훈을 주입한다. Actor(행동)·Evaluator(채점)·Self-Reflection(교훈 기록)의 3역할 구조.[^6]
- tick 실패/반송 시: "무엇이·왜 틀렸고 다음엔 어떻게" 한두 줄을 `loop_lessons`에 적재.
- 루프/`tick` 시작 시: 같은 loop_name·태그의 최근 교훈을 컨텍스트에 선별 주입.
- 자산: 에이전트 `loop-reflector`, 스킬 `loop-reflect`, DB `010_loop_lessons.sql`, MCP `loop_lesson_record`/`loop_lesson_search`, eval `reflection-memory`.
- 사후(루프 종료 후) 분석은 기존 `loop-postmortem`이 담당 — REFLECT는 **루프 도중**, postmortem은 **루프 이후**라는 점이 다르다.

> 3규율 한 줄: **짧게 보고(CONTEXT) · 헛돌면 멈추고(PROGRESS) · 틀리면 적어둔다(REFLECT).**

## 6. 루프 유형 분류
| 유형 | 특징 | 사람 개입 | 대표 사례 |
|---|---|---|---|
| **인터랙티브 루프** | 사람이 tick마다 보고 다음을 지시. 짧은 STOP | 매 tick | IDE에서 함께 디버깅, 페어 코딩 |
| **백그라운드 자율 루프** | 트리거가 알아서 돌고 사람은 REPORT만 확인 | 거의 없음 | 야간 의존성 업그레이드, CI 실패 자동수정 |
| **grade-revise 루프** | 별도 grader가 결과를 루브릭으로 채점, 미달 시 "다시 수정"으로 반송 | 기준 설정만 | 품질 게이트가 붙은 코드 생성 |
| **fan-out 루프** | 리드 에이전트가 수십~수백 서브에이전트로 병렬 분배 후 결과 수집 | 플랜 설계만 | 대규모 리팩토링, 멀티파일 일괄 수정 |

실무에서는 이들이 합쳐진다. 예: **fan-out + grade-revise + reflect** = 병렬로 만들고 grader가 골라내며 실패에서 교훈을 적어 다음 분배를 개선(V9 권장 조합). 패턴 선택 기준은 `루프_패턴_라이브러리.md` / 스킬 `loop-pattern-select`.

## 7. Claude Code 2026 네이티브 매핑
Claude Code의 네이티브 기능은 6요소·3규율·루프 유형과 1:1로 맞물린다.

| 네이티브 기능 | 하는 일 | 루프 매핑 |
|---|---|---|
| **Dynamic Workflows** | 리드가 한 세션에서 수십~수백 병렬 서브에이전트로 fan-out. 플랜은 **컨텍스트가 아닌 스크립트 변수**에 저장 → 지시 충실도 유지 | ACTION·SCOPE·BUDGET(병렬도) → **fan-out 루프**, CONTEXT(외부화) |
| **Performance Outcomes** | 별도 grader가 각 결과를 **루브릭으로 채점**, 미달 시 "다시 수정" 반송 | 곧 **grade-revise 루프** |
| **`/goal` (Completion conditions)** | 완료조건을 정하면 충족까지 여러 턴 자율 작업. **매 턴 끝에 별도 평가 모델이 목표 충족을 점검** | **STOP/BUDGET** + `loop-grader`·`loop-tick-stop-check` |
| **Hook** | 결정적 게이트(타입체크·정지조건·예산·무진행·컨텍스트)를 코드로 강제 → 환각 차단 | TRIGGER 판정·STOP·BUDGET·PROGRESS·CONTEXT 집행 |
| **Skill** | 반복 작업을 패키징해 재사용 | ACTION 묶음(loop-design/run/reflect/postmortem/pattern-select) |
| **Subagent memory / 외부 store** | 세션 간 상태·교훈 보존 | REFLECT(`loop_lessons`) |

> `/goal`은 2026-05 Claude Code에 도입된 완료조건 명령으로, 매 턴 끝에 평가 모델이 조건 충족을 판정한다 — 본 방법론의 STOP(결정적 판정)·grade-revise를 네이티브로 구현한 셈이다.[^4]

설계 원칙 셋:
1. **결정적 판정은 hook으로.** "정지/예산초과/무진행 여부" 같은 yes/no는 LLM에게 묻지 말고 hook(exit 0/1)으로 강제한다. false done(거짓 완료)을 막는다.
2. **플랜·상태는 컨텍스트가 아니라 변수/DB에.** 규모가 커질수록 컨텍스트에 매몰된 플랜은 지시 충실도를 무너뜨린다.
3. **자율 전에 통제(control before autonomy).** 테스트·권한·감사·롤백·사람리뷰를 먼저 갖춘 뒤 자율 단계를 올린다(§9).

## 8. 안티패턴
| 안티패턴 | 증상 | 처방 |
|---|---|---|
| **무한루프** | STOP이 주관적이라 영원히 돎 | STOP을 결정적 OR(목표 OR 횟수 OR 예산 OR 시간 OR 무진행) |
| **비용 폭발** | BUDGET 미설정으로 토큰/달러 폭주 | tick·누적 두 층 상한 + `loop-budget-cap.sh` |
| **헛도는 루프(no progress)** | 반복은 도는데 지표가 안 변함 | 델타 감지 + `loop-no-progress-check.sh` STOP |
| **컨텍스트 폭주/패닉** | 창이 차며 마무리를 서둘러 품질 저하 | 매 tick 압축·외부화·선별 주입(`loop-context-compact.sh`) |
| **자가증식(runaway fan-out)** | 서브에이전트가 또 서브에이전트를 무제한 생성 | 깊이·동시성 상한, 리드만 fan-out 권한 |
| **거짓 완료(false done)** | LLM이 검증 없이 "완료" 선언 | 완료는 hook/grader의 결정적 판정으로만 인정 |
| **기억상실(같은 실수 반복)** | 매 루프 처음부터, 과거 실패 미반영 | REFLECT — `loop_lessons` 적재·주입 |
| **보고 누락** | 무엇이 바뀌었는지 추적 불가 | REPORT 필수 + `loop_runs` 적재 |
| **모호한 ACTION** | "개선" 같은 비측정 목표 | 측정 가능한 행동·완료기준으로 치환 |

## 9. 자율성 사다리 — "통제가 먼저, 자율은 나중" (Anthropic 2026)
2026년은 단일 어시스턴트에서 **에이전트 팀 오케스트레이션**으로 넘어간 해다. 개발자는 업무의 ~60%에 AI를 쓰지만 "완전 위임"은 0~20%에 그친다 — 격차의 답은 **자율 전에 통제**다.[^4] 루프의 자율 단계를 올릴 때마다 통제 장치를 먼저 채운다.

| 사다리 | 루프 형태 | 먼저 갖출 통제 |
|---|---|---|
| 1. 인터랙티브 | 사람이 매 tick 확인 | 명확한 ACTION·STOP |
| 2. grade-revise | grader가 채점·반송 | 반증가능 루브릭, 결정적 검증 |
| 3. 백그라운드 자율 | 트리거가 알아서, REPORT만 확인 | BUDGET/STOP hook, 무진행 감지, 감사로그, `human_gate`(머지/롤백) |
| 4. 다중에이전트 오케스트레이션 | 리드가 fan-out, 교훈 누적 | 깊이·동시성 상한, 권한 분리(RBAC), 롤백 경로, REFLECT 메모리 |

오케스트레이션 4요소(보고서): **Objective**(왜 — 오케스트레이터에게) · **Outcomes**(각 에이전트의 "완료" 정의) · **Constraints**(건드리면 안 되는 것) · **Edge cases**(현실의 지저분함). 이는 본 방법론의 **ACTION/STOP·SCOPE·예외처리**에 그대로 대응한다. 실제로 Claude Code는 1,250만 줄 vLLM 코드베이스에서 7시간 자율 작업으로 복잡한 구현을 99.9% 수치 정확도로 완수한 사례가 보고됐다.[^4]

연결 흐름(V9 전형):
1. 목표 제시 → `loop-pattern-select`로 패턴 선택 → `loop-design`이 6요소 loop spec 생성
2. `loop-orchestrator`가 fan-out, 시작 시 `loop-reflector`가 관련 `loop_lessons` 주입
3. 각 tick: ACTION → `loop-grader` 채점 → 실패 시 `loop-reflector`가 교훈 적재 + revise
4. tick 경계: `loop-context-compact.sh`(컨텍스트) → `loop-no-progress-check.sh`(무진행) → `loop-budget-cap.sh`(예산) → `loop-tick-stop-check.sh`(STOP)
5. 종료: `loop-report-emit.sh`가 REPORT + `loop_runs` 적재 → 사후 `loop-postmortem`이 개선·eval 후보 도출
