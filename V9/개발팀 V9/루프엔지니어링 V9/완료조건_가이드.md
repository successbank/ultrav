# 완료조건 가이드 (STOP / Completion conditions 심화)

루프의 품질은 **"언제 멈추는가"** 에서 갈린다. 정지조건이 주관적이면 무한루프·비용폭발·거짓완료가 생긴다. 이 문서는 STOP을 결정적으로 설계하는 법을 다룬다.

## 1. 정지 조건의 종류
| 종류 | 의미 | 판정 방식 | 예 |
|---|---|---|---|
| **목표 달성** | 원하는 상태에 도달 | hook/grader의 결정적 판정 | 모든 CI green, 커버리지 ≥80% |
| **반복 상한** | 최대 tick 수 초과 | 카운터 비교 | iterations ≥ 10 |
| **토큰 상한** | 누적 토큰 초과 | 누적 합 비교 | tokens_used ≥ 200k |
| **비용 상한** | 누적 비용 초과 | 누적 합 비교 | cost_usd ≥ 5 |
| **시간 상한** | 경과 시간/마감시각 초과 | 시계 비교 | elapsed ≥ 60min, time ≥ 04:00 |
| **무진행(V9)** | 지표가 N tick 연속 개선 없음 | 델타 비교(hook) | no_progress_ticks ≥ 3 |
| **사람 개입** | 사람이 중단/거부 | 외부 신호 | 중단 버튼, 거부 코멘트 |

원칙: **STOP은 위 조건들의 OR 결합.** 목표가 영영 충족 안 돼도 반복/토큰/비용/시간 상한이 받아낸다.

```yaml
stop:
  any_of:
    - all_ci_green          # 목표
    - iterations >= 10      # 반복 상한
    - tokens_used >= 200000 # 토큰 상한
    - cost_usd >= 5         # 비용 상한
    - elapsed_min >= 60     # 시간 상한
    - no_progress_ticks >= 3 # 무진행(V9): 지표 개선 없음
    - human_abort           # 사람 개입
```

Claude Code의 **Completion conditions**는 경과시간·턴·토큰을 추적하며 조건 충족까지 자율 작업한다 — 위 OR 결합을 네이티브로 표현한 것이다. 2026-05 도입된 **`/goal`** 명령은 완료조건을 정하면 **매 턴 끝에 별도 평가 모델이 충족 여부를 점검**한다 — STOP의 결정적 판정과 grade-revise를 네이티브로 구현한 셈이다.

## 2. 결정적 판정을 위한 hook 사용
"정지조건 충족 여부"를 LLM에게 물으면 환각으로 잘못 종료(또는 종료 안 함)한다. **yes/no 판정은 hook(exit 0/1)으로 강제한다.**

- `loop-tick-stop-check.sh` — 매 tick STOP 평가. 충족 시 exit 1 → 루프 종료 신호.
- `loop-budget-cap.sh` — 누적 토큰/비용 상한 초과 시 exit 1 → 차단.
- `loop-no-progress-check.sh` (V9) — 지표(실패수·커버리지·grader 점수)가 N tick 연속 개선 없으면 exit 1 → 종료. "헛도는 루프"를 상한과 별개로 차단.

판정 데이터(반복 수·누적 토큰·비용)는 LLM의 기억이 아니라 **외부 상태**(스크립트 변수/`loop_runs`/환경변수)에서 읽는다. 이는 Dynamic Workflows가 "플랜을 컨텍스트가 아닌 변수에 둔다"는 원칙과 동일하다.

## 3. grade-revise 루브릭 작성법
grade-revise 루프에서는 grader(`loop-grader`)가 결과를 채점하고 미달 시 "다시 수정"으로 반송한다. 루브릭은 **객관적·이진 판정 가능**해야 한다.

좋은 루브릭의 조건:
1. **통과선이 숫자/조건**으로 정의됨 (예: "테스트가 실패→통과로 바뀌고 커버리지 ≥80%")
2. **거짓으로 통과시킬 수 없음** (예: "테스트를 삭제해 green 만들기" 금지 명시)
3. **채점 결과가 구조화된 JSON** — `{score, pass, feedback}`

grader 출력 계약(고정):
```json
{ "score": 0.0~1.0, "pass": true|false, "feedback": "미달 시 무엇을 어떻게 고칠지" }
```
- `pass=false`면 `feedback`을 포함해 ACTION으로 반송(revise).
- `pass=true`라도 STOP의 다른 상한(예산·시간)이 우선하면 종료.

루브릭 예(테스트 커버리지 루프):
> 신규 테스트가 (1) 실제 미커버 분기를 커버하고 (2) 전부 통과하며 (3) 기존 테스트를 삭제/약화하지 않았는가. 셋 다 충족 시 pass.

## 4. 거짓 완료(false done) 방지
LLM이 검증 없이 "완료했습니다"라고 선언하는 것이 false done이다. 다음으로 막는다.

| 방어선 | 방법 |
|---|---|
| **완료 권한 분리** | "완료" 선언 권한을 실행 LLM이 아닌 hook/grader에 둔다 |
| **결정적 검증** | 목표 달성은 명령 실행 결과(테스트 exit code, 커버리지 수치)로 확인 |
| **반증 가능 루브릭** | grader가 "통과시킬 핑계"를 못 대도록 금지조건 명시(테스트 삭제 등) |
| **상한 안전망** | 목표 판정이 흔들려도 반복/예산/시간 상한이 종료를 보장 |
| **기록 대조** | `loop_runs`의 `outcome`·`stop_reason`을 사후 `loop-postmortem`이 검증 |

## 5. 정지조건 설계 절차(요약)
1. **목표 조건**을 코드로 판정 가능하게 정의(테스트/커버리지/CI 상태).
2. **상한 4종**(반복·토큰·비용·시간) 중 최소 2개를 OR로 추가.
3. **사람 개입** 신호(중단/거부)를 OR에 포함.
4. 판정을 `loop-tick-stop-check.sh` + `loop-budget-cap.sh`로 hook화.
5. grade-revise면 루브릭을 `{score, pass, feedback}` 계약으로 고정.
6. 종료 시 `stop_reason`을 `loop_runs`에 기록 → postmortem에서 거짓완료 여부 대조.

> 한 줄 원칙: **목표로 멈추되, 상한으로 보장하라. 완료 판정은 사람·hook·grader가 하고 LLM이 하지 않는다.**
